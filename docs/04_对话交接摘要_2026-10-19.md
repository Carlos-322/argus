# 04 Argus 现在怎样标注，以及我们要怎样改

更新日期：2026-10-21。本文只讲当前流程、希望增加的人工提示词模式，以及两个指定版本的区别。

## 1. 先说结论

我们要的方式是：**人先读标注规范，写好“有哪些子任务、每段怎么开始和结束、哪些情况无效”，再让模型根据这些要求，在 MCAP 的画面中找到对应片段。**

两个版本都已经会在调用标注模型前准备提示词。但目前用的是 Argus 自带的通用标注要求，还不是我们按加热、加小料规范写好的专用要求。

`758c5555` 比 `b1e74c40` 增加了评分、传感器分析和页面功能，也修改了默认调用和重试方式，详见第 5 节。但它没有直接增加上述业务模式；只升级版本，仍不能自动得到按我们规范划分的结果。

本次查看时，本地实际运行代码所在的提交仍是 `b1e74c40`。下面同时对照 Git 中保存的 `758c5555` 源码；没有切换或升级本地版本。

## 2. 现在 Argus 是怎样划分和标注的？

可以把主要过程看成五步：

| 步骤 | 实际做什么 |
| --- | --- |
| 1. 读取 MCAP | 在本地读出相机画面、时间信息，以及能使用的机器人状态和传感器记录。 |
| 2. 准备模型要看的材料 | 按一定间隔抽取画面，加上时间和文字说明。录制很长时，会分成几批处理。 |
| 3. 准备提示词 | 加入 Argus 自带的标注要求、这段录制的任务说明、输出格式，以及可用的数据说明。 |
| 4. 调用模型 | 模型看这些材料，判断发生了哪些动作，给出每段的起止时间、动作描述和相关问题。 |
| 5. 整理结果 | 把分批结果放回原录制的时间线上，保存为标注文件，并在查看页面展示。 |

**MCAP 文件通常不是直接整包发给模型。**Argus 先从中准备图片、文字和可用信号，再通过 API 发送。字段含义不明确、需要补充证据等情况下，还可能有额外模型调用。

现在的默认分段要求，大致是：伸手、抓取、搬运、放置、松爪、回撤等不同动作，分别记录成段。因此，我们业务上的一段“放雪克杯”，可能会被它分成“搬运杯子、放下杯子、松爪、撤开夹爪”等几段。

它不是毫无要求地自由回答，而是**按作者写好的通用动作规则标注**。问题在于，这套通用规则和我们文档中的业务段落不完全一致。

还有两个容易混淆的地方：

- **分批处理不等于业务分段。**长录制为了发给模型而拆成几批，不代表每一批就是一个子任务。
- **给出秒数不等于已经逐帧确认。**模型主要看抽样画面；即使输出了精确小数，也不代表那个时刻的原始帧已经检查过。

## 3. 我们希望改成什么方式？

```text
人阅读加热 / 加小料标注规范
             ↓
人提前写好对应的提示词，保存为文件
             ↓
本次选择使用哪一份提示词，并选择 MCAP
             ↓
Argus 读取 MCAP，准备画面、时间和可用信号
             ↓
把人工写好的规则与这些材料一起交给标注模型
             ↓
模型按指定子任务寻找片段，输出名称、起止时间和结果
             ↓
检查输出，再由人查看和修改
```

这里“人提前给出分段要求”，指的是提前规定**段落的种类和边界判断方法**，不是要求人先把实际起止帧标完。具体在第几秒开始、结束，仍由模型结合录制判断。

例如，加小料文档已经规定六种子任务：

1. 放雪克杯。
2. 夹取小料勺。
3. 舀取小料。
4. 倒入小料。
5. 放回小料勺。
6. 取杯回 Home。

人需要把这些名称以及起止条件写进提示词。模型的工作是去找这六类动作实际发生的位置。没有录到的步骤不能补造；实际发生了重复、失败或其他异常，也要如实记录。

**不需要每次运行都让 AI 先读 PDF、再替我们决定规则。**第一步可以很简单：人根据文档写好两份提示词，加热用一份，加小料用另一份，之后按工位重复使用。规范有变化时，再人工修改对应提示词。

### 人工提示词可以这样写

下面以当前 1 号加小料数据为例，展示提示词需要表达的内容。完整边界依据见 [02 工位规则](02_加热与加小料标注规则.md)。

```text
你要按下面的业务规则，为这段机器人录制划分子任务。
画面和信号将在后面提供，每份材料都带有时间信息。

本次任务：右臂放下雪克杯，使用1号小料勺从1号料盒舀料，
倒入雪克杯，放回勺子，最后持杯回到 Home。
勺号与料盒号分别记录，本次两者均为1。

只使用以下六种子任务名称，并按对应边界判断：
1. 奶茶：放雪克杯
   从右臂持杯开始向杯架运动，到松开杯子并将夹爪移至杯口上方。
2. 奶茶：夹取小料勺
   从上一段结束，到1号小料勺被夹住并离开放置位。
3. 奶茶：舀取小料
   从上一段结束，到勺头向下、向前完成舀取，但尚未往上抬。
4. 奶茶：倒入小料
   从开始抬勺，到完成倾倒或抖料，勺头离开并高于杯口。
   抬勺和移向雪克杯的过程属于这一段。
5. 奶茶：放回小料勺
   从上一段结束，到勺子放稳，夹爪松开并离开勺柄。
6. 奶茶：取杯回 Home
   从上一段结束，到右臂夹取雪克杯并持杯回到 Home，稳定停止。

等待和微调归当前子任务；下一子任务从有明确目标的运动开始。
若具体边界条件与这条规则在画面上无法统一，请说明冲突，不要猜。
子任务区间不得重叠。同一个边界时刻只分配给一侧。
只标实际发生的动作，不补全未录到的步骤。
不要把抓取、松爪等细动作额外列成新的业务子任务。

动作成功必须有物体状态证据，不能仅凭手臂走完路线判断。
失败、不可判定、空载演示、人工介入，按本规范标为无效并说明原因。
重复尝试要如实记录，不要只保留最后成功的一次。

请返回：子任务名称、开始时间、结束时间、动作描述、
成功/失败/不可判定、是否无效、判断依据和需要人工查看的问题。
时间使用提供材料的时间轴；不能确认的边界保留候选范围。
```

这是所希望增加的提示词模式示例，本轮尚未把它接入程序。加热工位要使用另一份提示词，其中“离开触控板”的结束位置等未明确内容，应先补充或保留为人工确认项。

## 4. 现在能不能提前写提示词？还需要改哪里？

**能提前写；目前也有文字输入入口。但要稳定按我们的业务段落输出，需要调整默认提示词和结果处理。**

| 现有方式 | 能做到什么 | 还缺什么 |
| --- | --- | --- |
| `--dataset-note` | 在标注前，把人填写的文字作为背景说明交给模型；可以先用来试验规则的影响。 | 原有“不同抓取、释放等动作分别成段”的要求仍然存在，两套要求可能冲突。 |
| 录制中的任务说明 | 告诉模型这段录制原本打算做什么。 | 不等于完整的分段规范，仍需明确子任务名称和边界。 |
| 修改内置提示词 | 可以直接改变模型收到的标注要求。 | 每次换工位都改代码不方便，也容易把通用规则和业务规则混在一起。 |

两个版本的相关命令入口中，都没有发现一个现成的“选择人工业务提示词文件，并按其中固定子任务输出”的完整模式。现有的示例标注入口用于展示输出示例，也不等于替换整套业务规则。

第一版只需要围绕这条主线改：

1. **读取人工提示词文件。**运行前选择加热或加小料；标注前能查看本次真正会发出的提示词。
2. **让业务规则接管分段要求。**保留图片、时间等必要说明，调整原来与业务规则冲突的动作拆分要求，不能只在末尾再加一句话。
3. **接住并检查模型结果。**检查名称是否在允许列表中、时间是否有效、是否出现不允许的重叠，以及无效原因有没有保存。标注结果必须能在本地查看。

两份提示词先由人维护即可。自动解析 PDF、平台对接和独立 MCAP 子文件导出，都不是实现这条流程的必要前提。

## 5. 从 `b1e74c40` 到 `758c5555`，到底改了什么？

**有执行和使用逻辑上的改动，而且不只涉及提示词。基本入口没换，但默认调用哪些模型步骤、怎样处理失败、怎样判断子目标和怎样展示结果，都有变化。**

### 5.1 这次比较的范围

- `758c5555` 中有 **257 个 `b1e74c40` 没有的提交**：222 个非合并提交、35 个合并提交；沿主线看是 25 次整合更新，对应 PR #48 至 #72。
- 两个提交的最终文件差异为 **239 个文件，新增 33,844 行、删除 3,077 行**，其中包含大量测试、测试数据和文档，不能当成 257 项新功能。
- 它们不是一条直线上简单相邻的新旧版本：共同基础是 `0f6d2e97`，`b1e74c40` 另外包含本地 DeepSeek 接入和运行脚本等改动。这部分差异单独看，不能误认为上游删除了你的功能。

### 5.2 新增和增强了哪些功能？

| 内容 | 改了什么 | 使用时会看到什么变化 |
| --- | --- | --- |
| **质量评分** | 新增根据已有标注计算的 0-10 分评分：任务结果、执行质量，以及子目标的执行质量。执行质量考虑错误、停顿和用时等。 | 页面多出评分，可以辅助比较录制。分数由程序根据标注计算，不是再请模型独立验收；标注不完整或缺少比较依据时，部分分数不显示。 |
| **触觉、压力和深度分析** | 增强触觉阵列的单点、区域和跨时刻比较；把相关相机画面与传感器读数配合起来，部分触觉数据增加单独分析。 | 有这类数据时，能得到更细的传感器说明；模型调用次数可能增加。旧版本已经支持传感器，新版是扩展分析能力。 |
| **视频上的传感器说明** | 在适用的传感器流程中增加标注后的文字调用，选择和改写说明卡片，同一时刻最多展示两张。 | 视频说明更简短，全部发现仍保留在列表和导出中；卡片调用失败不会丢掉已完成的标注。 |
| **数据读取和坏数据处理** | 继续加强部分相机损坏、ZIP 内容异常、MCAP 单条消息或元数据异常时的处理；保留其他可读内容并说明遗漏。 | 某一部分损坏时，整条录制或整个批次更有机会继续处理，而不是全部中止。 |
| **时间和单位处理** | 修正时间戳单位、视频末帧、画面与标注显示时机；统一关节角度的度/弧度处理。声明与数值冲突时保留记录并避开不适用的运动检查。 | 同步、运动分析和边界证据可能与旧版不同，这些修复会间接影响标注结果。 |
| **模型收到的信号内容** | 减少重复信号文字，重点保留指令和实际状态不一致的位置；不能逐时刻可靠表达的信号，按条件提供窗口均值或极值时间。 | 同一个 MCAP，模型收到的文字和读数不一定与旧版一样；这也会影响费用和判断。 |
| **结果页面和批量进度** | 新增已标注条数/时长相对目标的进度；页面每 30 秒检查重建后的结果；重建时复用未变的单条记录。 | 可边跑边看进度；重建大批结果更省时间；session 页面会显示原始任务说明。 |
| **检查和运行稳定性** | 明确区分“查出问题、未查出问题、不适用、执行出错”；改善检查进程异常、视频转码进度与线程分配。 | 检查失败不会被当作检查通过，单条处理出错也更容易与其他任务隔离。 |

此外，自动化测试改成按耗时分成八组并行运行，补充了大量回归测试；README 增加完整参数说明和 DiverseUMI 数据发布介绍。这些不是标注业务模式的改造。

### 5.3 哪些使用行为真的变了？

**① 可以控制标注前的两类辅助调用。**

新版新增：

| 参数 | 作用 |
| --- | --- |
| `--field-dictionary off` | 跳过“让模型解释不明确的数据字段”这一步。默认仍为 `on`。 |
| `--inspection auto` | 新作业默认值：对深度、触觉，以及普通提示词没能带上的某些字段，进行额外证据检查。 |
| `--inspection all` | 让只有普通手臂状态、动作、腕部力矩等字段的录制也进入额外检查。 |
| `--inspection off` | 关闭证据选择调用。并不等于关闭主标注，也不保证关闭所有辅助调用；触觉阵列的单独区域分析仍可能执行。 |

旧版没有这两个用户开关，默认对有可用额外字段的录制更广泛地启动检查。新版对只有手臂信号和腕部力/力矩的录制，通常不再默认做这一步，但抽样读数仍会发给模型。如果还有只能通过额外检查读取的字段，则仍可能触发自动检查。

所以，同样一条旧命令，在**新建作业**时也可能产生不同的调用次数。已有作业继续运行时保留保存的设置，不会简单全部切成新默认值。

**② 模型默认设置和费用控制有调整。**

- Astra 默认仍使用 medium；其他模型统一默认 high。旧版只有部分模型默认 high。
- 为若干辅助调用单独留出推理所需的输出额度，减少推理占满额度后没有足够空间写答案的问题。
- 通过 OpenRouter 使用 Gemini 时，价格检查不再因为请求没有使用的音频或按需搜索价格项就拒绝运行。这里是接入和预算校验的改进，不代表本次验证过模型效果。
- 对比的 `758c5555` 中，字段解释和遥操画面分辨率选择使用固定模型，不会自动随主标注的 `--model` 一起变。它也没有本地 DeepSeek 适配；升级时需要一起核对这些调用。

**③ 供应商失败后，会有限自动重发。**

旧版对已经发出、可能收费却没拿到完整结果的请求，通常需要显式允许再发。新版识别出供应商错误、请求没有完整返回等情况后，最多再发两次，等待时间为 30 秒、120 秒。

每次可能产生的费用仍计入预算，重发不等于免费。模型自己写出的无效 JSON、因输出长度上限而截断的回答，不在这类自动重发范围内，仍需要人工决定是否重试。

**④ 子目标和多轮任务的判断要求变了。**

- 新版更明确地要求：子目标是完成后能保持的状态变化，比如松手后杯子仍放好了；抓住物体或碰一下，本身不算这样的子目标。后续微调不重复生成同一个子目标。
- 在 `session` 模式中，一次任务完成后重新做一遍，应作为另一个任务；为完成同一目标而做的多个阶段仍属于同一个任务。
- 长录制分批标注后，改进任务结果的合并，并避免仅因两批都出现“杯子”这个名称，就把不同杯子合成同一个物体。

这些变化可能改变事件数量、任务数量、完成时间和评分。但它们不是“加热必须按指定六类子任务标注”的功能；新版子目标也不能直接当作你的业务子任务。

**⑤ 继续旧作业和查看结果时要区分两件事。**

- 继续旧作业，会保留旧的输入和设置。要比较新版读取效果或新的标注设置，应使用新的输出目录；重建结果页面本身不会重新标注。
- 结果页面可以自动看到重建后的变化；新增的缓存让未改动记录不必重复生成。需要全部重建时有 `board build --no-cache`。

### 5.4 删除了什么？哪些只是分支差异？

| 类型 | 具体内容 | 意味着什么 |
| --- | --- | --- |
| 真正的旧代码清理 | 删除未使用函数、常量、重复工具代码，以及一个实际不会执行的上传适配分支。 | 主要是维护和去重；公共数据集下载入口仍在，不能理解为删除了 MCAP 或这些数据集的支持。 |
| 仓库素材删除 | 上游删除旧 `media/board.gif` 演示文件。 | 不影响标注功能。 |
| 两个提交之间的本地适配差异 | `758c5555` 中没有本地 `label/providers.py`、DeepSeek 测试、`local-dev` 脚本、Windows 启动入口和环境说明。 | 这些原本是本地分支独有内容，不是上游这轮专门删掉的。直接换成该提交，不能假定原来的 DeepSeek 启动方法仍可用。 |

两个版本的 `pyproject.toml` 和 `uv.lock` 没有变化。本轮的主要工作是程序逻辑、测试和展示层更新，不是换了一整套依赖或要求先训练模型。

### 5.5 哪些主要用法没变？

- 基本入口仍是 `review` 读取自己的数据、调用模型标注，再用 `board serve` 查看结果。
- MCAP 仍先在本地解析成画面、时间和信号，不是要求把它预先人工标注好。
- 通用动作分段的核心文字 `LEAN_NOTE` 在两个提交中完全相同；默认采样间隔也没有因这轮更新整体改成逐帧分析。
- `--dataset-note` 仍是给模型补充背景文字。没有新增一个完整的“载入人工业务提示词文件，严格按工位子任务和边界输出”的模式。

对你的实际影响是：**基础操作步骤相近，但默认检查范围、模型调用、失败重试、子目标判断和输出内容确实变了。要按两份标注规范划分，仍需另做人工提示词模式；要使用新版其他改进，则需保留本地 DeepSeek 适配后再验证。**

以上来自两个指定提交及中间历史的源码对比，没有重新运行收费标注，也没有验证新版效果一定优于旧版。

## 6. 这个需求应该怎样推进？

先把**人工提示词文件 → 按业务规则调用模型 → 查看结果**这条流程做通。可以在已有本地版本上做，也可以在合入新版改进后做；升级并不是它的必要条件。

先选一份对应工位的 MCAP，查看实际发出的提示词，再检查输出是否使用规定名称、是否按规定边界划分。对切点不准的地方补看附近连续帧，逐步改进。只在提示词里写“精确到帧”，并不会自动获得帧级精度。
