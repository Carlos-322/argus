# 01 按加热规范分段和标注

## 1. 当前使用什么规则

从 2026-10-26 起，加热菜单默认使用 [加热工位人工核对分段规范](加热工位人工核对分段规范.md)，配置名为 `heating-review-20261026`。六个中文标签沿用以前的名称，更新的是每段的起止判据。

**先由人写好规则，再让 Argus 把规则和录制画面一起发给模型，由模型按规则定位时间。** 不需要给每条 MCAP 单独写提示词，也不要求 MCAP 自带提示词。具体规则见 [02](02_加热与加小料标注规则.md)。

相对于以前默认的“完整六段”模式：

| 项目 | 现在的要求 |
| --- | --- |
| 段数 | 只标实际发生且能定位的步骤；未观察到的逐项说明，不强行凑六段 |
| H4 结束 | 在同一参考机位中，整个左夹爪首次低于显示屏下边缘 |
| 参考机位 | 模型根据画面选择，并在 H4 结束证据中写明机位及依据 |
| H5 结束 | 左手持纸杯回到 Home 并停止，不再等右臂回退 |
| H5 与 H6 | 分别判断，不强制相接；实际有空档或重叠就如实保留 |
| 看不清 | 标记不确定并解释，无法定位时说明缺失，不编造动作 |

H1→H2→H3→H4→H5 明确衔接的相邻步骤仍共用切点。H4 的 1–1.5 秒只是参考，不能用它代替画面判断。

## 2. 怎样标注前三条

1. 双击项目根目录的 [启动Argus.cmd](../启动Argus.cmd)，主菜单输入 `1`。
2. 选择条目时输入 `1-3`。也可以输入单个编号、`1 3 5` 或 `all`。
3. 选 `1`：只准备请求，不调用 API；选 `2`：正式调用模型标注。
4. 正式标注时填写每条预算，核对条目后输入 `y`，按提示在本机隐藏输入 API Key。
5. 完成后回主菜单选 `2` 查看结果。已经打开的结果列表可输入 `r` 刷新。

命令行也可以操作（在主菜单输入 `3` 后执行）：

```bash
# 准备前三条的请求，不调用 API
bash local-dev/heating-samples.sh --samples 001 002 003

# 正式标注前三条，每条预算 1 美元
bash local-dev/heating-samples.sh --samples 001 002 003 --run-api --cap 1
```

其他加热 MCAP 使用下面的入口。示例只准备请求；正式标注时去掉 `--free` 并设置预算。

```bash
bash local-dev/review-heating.sh --data "/mnt/d/你的目录/录制.mcap" --out ./data/review/加热_新批次 --free --jobs 1 --concurrency 1
```

直接调用 `python -m review` 时，需要明确加上 `--annotation-spec heating-review-20261026`；通用入口不会自动套用加热规则。

## 3. 程序实际怎样工作

**读取 MCAP → 转换视频和时间映射 → 抽取画面 → 加入预先写好的规则 → 模型返回时间段 → 检查结果格式和时间关系 → 保存并展示。**

这批 20 条样本只向读取器传入所选 MCAP，旁边下载的人工答案和对照 HTML 不发给模型。规则内容在调用前已确定，模型负责根据画面定位，不负责重新制定分段标准。

程序检查标签是否合法、时间是否越界、缺失步骤是否有解释，以及规定的切点是否衔接。新模式允许同一轮 H5/H6 实际重叠，其他步骤仍不能重叠。检查通过表示格式可用，不能证明视觉判断正确。

原有输出格式保持不变：每段保留起止时间、起止证据和不确定说明，中文标签和模板描述由配置补入。模板描述不是模型对动作成功的证明；复核时应查看证据和原视频。

目前加热模式仍以一条完整录制构建一次请求，不支持把长录制拆成多个技术窗口后套用本规则。源规范提到的跨窗口要求是后续扩展时的约束，本次没有新增跨窗口能力。超过当前请求容量时会在调用前停止，需要调整采样或输入范围。

默认每秒抽取 4 次画面，输出是供人工核对的候选边界，不是逐帧精确答案。H4 遮挡、显示屏下沿不可见或采样跨过关键动作时，仍需人工复核。

## 4. 结果和旧批次怎样区分

双击 [查看已有结果.cmd](../查看已有结果.cmd)。新结果的标题末尾显示“10月26日分段规范”；旧结果仍显示原来的规则名称。

每次默认在 `data/review/` 下新建带时间的批次，每条录制单独保存。目录前缀仍为 `heating_v2_`，实际规则以标题及 `annotation_policy.json` 为准。

| 文件 | 可以查看什么 |
| --- | --- |
| `annotation_policy.json` | 本次规则版本、完整内容及内容校验值 |
| `dry/` | 调用前准备的请求记录，没有模型答案 |
| `run/out/` | 模型回复、校验结果和费用记录；失败时先查看原因 |
| `qa/`、`clips/` | 结果网页使用的标注和视频 |

旧的 `heating-v2` 和 `heating-v2-complete` 配置保留，供查看、复现旧批次。它们不会自动变成新标准；更换规则要新建输出目录。平台下载的人工答案也不会被这次更新改写，比较时需注意它们是否仍按旧标准标注。

## 5. 以后怎样改规则

规范原文保存在 [加热工位人工核对分段规范.md](加热工位人工核对分段规范.md)，程序读取的配置是 [heating-review-20261026.json](../configs/annotation_specs/heating-review-20261026.json)。配置包含原文、六种标签和边界要求，会在调用前进入提示词。

修改规则时要同步原文、配置及配置内的来源校验值；必要时更新程序中的时间关系检查。仅改一份说明文档不会自动改变程序行为。程序检测到来源文档与配置不一致时会停止，避免使用不一致的规则。

加热入口默认复用 `data/cache/prepared_mcap/` 中的转换视频和时间映射。改提示词、标签、模型或抽帧频率时仍可复用转换结果，再准备新的请求；改原始数据、转换设置或缓存损坏时会重新转换。需要主动重新转换可加 `--no-preparation-cache`。

加小料规则仍只记录在 02 中，尚未接入这个加热入口。
