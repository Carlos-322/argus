# 01 按加热规范分段和标注

## 1. 现在要做什么

数据先经过上游质检，再交给 Argus。你已经提供了标注规范，**不需要为每条 MCAP 再手写一次提示词或配置六个标签**。

当前默认的 `heating-v2-complete` 模式使用 [加热工位标注规范](加热工位标注规范-1019-v2.pdf) 第 2–3 页的新版六子任务：

1. 奶茶：抵加热位保持
2. 奶茶：放纸杯腾左手
3. 奶茶：触控板按键
4. 奶茶：离开触控板
5. 奶茶：左手取回纸杯
6. 奶茶：从加热位撤回

旧的五子任务表不用于新模式。加小料模式尚未接入，仍可在 02 中查阅其规则。

## 2. 程序怎样工作

**首次读取 MCAP 并保存转换缓存 → 后续复用视频和时间映射 → 按本次配置抽帧、加入规范与提示词 → 模型定位子任务 → 程序校验 → 保存结果并在网页展示。**

### 同一条数据不用反复转换

加热样本菜单和 `review-heating.sh` 默认使用 `data/cache/prepared_mcap/` 保存转换缓存。
每次标注仍使用新结果目录，旧答案和旧费用记录不会带入新批次。

| 这次改了什么 | 是否重新转换 MCAP |
| --- | --- |
| 提示词、六段标签规则、模型、推理设置 | 不转换；复用视频和时间映射，重新准备标注请求 |
| 抽帧频率 | 不转换；在已有视频上重新抽帧 |
| 原始 MCAP 或读取器使用的配套源文件 | 重新转换 |
| 录制读取范围、rig、分组配置或转换代码 | 重新转换 |
| 缓存中的视频或时间文件缺失、损坏 | 重新准备，不使用损坏内容 |

程序会校验源文件内容和缓存文件。首次启用时，也会检查 `data/review/` 下已有批次；
源文件、转换代码和产物校验都一致，且旧任务没有运行时，可从已有视频建立缓存。
旧批次缺少完整记录或不兼容时仍会转换一次。旧记录对大文件只保存大小和修改时间，
首次导入沿用该校验；建立新缓存后会保存完整内容哈希。

看到 `reused cached videos and time mappings` 表示已跳过转换。复用仍需校验和复制文件，
也仍会运行检查、生成展示视频和准备请求，因此不会立即进入模型调用。
本次只优化转换复用，没有减少相机、传感器范围或取消其他检查。

修改规范后重新从菜单发起即可。命令行示例（默认只预演，不调用 API）：

```bash
bash local-dev/heating-samples.sh --samples 002 --sample-fps 2
```

需要忽略共享缓存、重新转换时：

```bash
bash local-dev/heating-samples.sh --samples 002 --no-preparation-cache
```

直接使用 `python -m review` 时，添加 `--preparation-cache data/cache/prepared_mcap` 启用复用。
必要时用 `--reuse-prepared 旧任务目录` 指定一个候选旧批次中的单条任务目录，它仍需通过校验。
改变标注配置必须使用新的 `--out`；原目录继续保留严格的恢复检查，防止覆盖已有付费结果。

本次用 002 的已有结果验证：首次导入缓存并准备新目录约 40 秒，第二次复用约 20 秒。
将抽帧频率从每秒 4 次改为 2 次后，视频和时间映射仍逐项一致，旧结果未修改。
这里仅测转换准备，不含后续检查、展示视频、请求准备及模型调用；验证没有调用付费 API。
缓存专项 11 项测试通过，相关回归 98 项通过（两组包含重叠测试）。

| 以前的通用模式 | 现在的加热模式 |
| --- | --- |
| 模型自行描述动作并决定标签名称 | 模型只能引用 H1–H6，程序填入规范中的准确名称和描述 |
| 按抓取、释放等动作自由分段 | 按给定的业务子任务及起止条件分段 |
| 用通用提示词判断任务 | 使用新版加热规范中的等待归属、按键、回撤等规则 |
| 主要检查回复能否解析 | 还检查标签合法、区间不重叠、不越界，以及缺失步骤是否说明 |

H3 包含去按触控板和按键停顿；H4 从首次离开触控板开始，单独成段。H5 按右臂准备回退界定结束，H6 保留持杯回 Home 的过程。

你已明确这批录制经过质检，包含完整六步。因此当前默认要求 **H1–H6 按顺序各输出一段，相邻段共享切点，中间不能漏掉内容**。看不清时根据前后动作给出候选边界并注明待复核，不能以“未观察到”为由省略 H5 等步骤。缺段、重复、顺序错误或中间留空的回复会校验失败，保留原回复，不算成功标注，也不会自动付费重试。疑似异常只供复核，不自动排除数据。

此完整性要求来自你的本批数据前提。旧的 `heating-v2` 规则保留供历史结果和已启动的旧批次使用；重新从 CMD 菜单发起的批次使用新规则。强制六段不代表边界已经准确，仍需与人工标注对比。

本次划分输出的是原录制时间轴上的片段区间，**不会生成六个独立 MCAP 文件**。

## 3. 20 条测试数据怎样运行

双击项目根目录的 `启动Argus.cmd`，在菜单输入 `1`。窗口会列出 20 条样本，让你输入要处理的编号：

| 想处理的数据 | 输入示例 |
| --- | --- |
| 第 017 条 | `17` |
| 第 001、003、005 条 | `1 3 5` 或 `1,3,5` |
| 第 001 至 005 条 | `1-5` |
| 全部 20 条 | `all` |
| 返回菜单 | `q` |

然后选择 `1`（dry run）或 `2`（正式 API 标注）。正式标注会再询问每条预算，显示本批总预算，输入 `y` 后开始；缺少 Key 时会提示隐藏输入。条目依次处理，完成后回到菜单，可选“查看已有结果”。

20 条样本从已有下载清单读取，只把选中的 MCAP 交给读取器，旁边的人工标注 JSON 和对照 HTML 不作为答案发给模型。

**以下是手动命令方式，使用前在主菜单输入 `3` 进入命令行。** 使用上面的选择菜单时不需要输入这些命令。

列出编号：

```bash
bash local-dev/heating-samples.sh --list
```

先检查第 001 条的请求（默认就是 dry run，不需要 Key）：

```bash
bash local-dev/heating-samples.sh --samples 001
```

对第 001 条实际调用 DeepSeek：

```bash
bash local-dev/heating-samples.sh --samples 001 --run-api --cap 1
```

只会在本机提示输入 Key；不要把 Key 写到命令或文档里。`--cap 1` 表示每条录制最多预留 1 美元，不保证一定够完成。达到上限或失败会保留记录。

选择几条：把编号写成 `--samples 001 002 003`。全部 20 条：使用 `--samples all`；默认仍是 dry run，只有加 `--run-api` 才实际发送。全部运行时，预算按条计算，例如 20 条、每条上限 1 美元，本批上限就是 20 美元。

每次默认新建带时间的批次目录：`data/review/heating_v2_模式_时间/`，下面每条录制一个目录。也可以通过 `--out` 指定批次目录；重用旧目录会按现有规则检查是否可恢复。

## 4. 其他加热 MCAP 怎样运行

```bash
bash local-dev/review-heating.sh --data "/mnt/d/你的目录/录制.mcap" --out ./data/review/加热_新批次 --free --jobs 1 --concurrency 1
```

上面是 dry run。正式标注时去掉 `--free`，加 `--cap 1` 等预算。这个入口已经选好六子任务规范，不必再次填写六个标签。

普通 `review-deepseek.sh` 仍保留通用模式；处理加热规范时请使用这里的加热入口。也可以直接给 `python -m review` 增加 `--annotation-spec heating-v2-complete`。

## 5. 结果怎样查看和复盘

正式流程生成看板后，双击 [查看已有结果.cmd](../查看已有结果.cmd)。新批次及其中每条录制会自动出现在列表，已打开的菜单输入 `r` 刷新。

网页时间线显示规范中的中文标签。新增的“加热工位：六子任务标注”区域显示每段的起止证据、没有定位到的步骤、规范异常及待复核原因。

如果窗口显示“标注失败”，先看紧随其后的具体原因，不要直接重跑付费标注。模型回复会保存在 `run/out/`；格式问题有时可以离线重新读取并恢复网页，无需再次调用 API。已兼容“异常只返回名称、没有理由”的回复，页面会明确标记理由缺失、需要复核；六段缺失、区间重叠或越界仍会校验失败。

| 文件 | 用途 |
| --- | --- |
| 每条任务的 `annotation_policy.json` | 保存实际使用的规范内容、版本和哈希 |
| `dry/` | 保存准备好的提示词与请求记录；没有模型答案 |
| `run/out/` | 模型原回复、校验结果及费用记录 |
| `qa/`、`clips/` | 网页所需的标注和视频 |

规范内容变化后，不会悄悄把旧规范的结果当成新结果。应选择新输出目录；历史结果仍可查看。

## 6. 当前边界和限制

- 默认每秒采样 4 次，模型输出秒级候选边界。输出小数不代表已经达到逐帧准确，需要对照视频复核。
- PDF 中 H4 结束写的是“左臂从触控板离开（原子任务3结束的位置）”，没有唯一的结束姿态。程序保留原文，并把 H4/H5 交界标为待复核，不自行增加距离或停顿阈值。
- 目前每条加热录制用一次完整请求，不把技术分块当作子任务切点。默认采样配置支持最长 165 秒；这 20 条最长约 102 秒，都在范围内。超出窗口会在模型调用前停止，需调整采样参数后再运行。
- 规则和格式校验不等于语义验收。真实模型的分段效果，需要实际 API 标注后与现有人工标注对照评估。

规则定义位于 [heating-v2-complete.json](../configs/annotation_specs/heating-v2-complete.json)，对应的中文规则说明见 [02](02_加热与加小料标注规则.md)。

## 7. 提供人工标注示例

完整示例可以帮助模型理解动作与切点，但不能保证降低误差。合适的示例应同时提供一条 MCAP、六段人工时间、边界附近的画面和判定理由。模型需根据目标录制重新定位，不能照搬示例秒数。示例与评估数据应分开；如果从这 20 条中选一条作示例，该条应排除在独立评估之外。

目前规范模式尚未接入示例输入；旁边的人工标注仍只用于标注后的对比，不会自动发送给模型。
